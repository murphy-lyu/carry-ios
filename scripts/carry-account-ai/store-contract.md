# Carry Account AI persistence and authorization contract

This directory is an un-deployed protocol/domain implementation. `createAccountAIHandler` has **no default Worker export and no memory production fallback**. A transactionally durable store and first-party identity boundary must be installed. The test fixture is explicitly `synthetic-only` and cannot be used without the handler's explicit synthetic option. No native `auth.sessions` rows may be forged; OAuth does not call native-only data/assets RPCs.

## Identity and OAuth

The issuer is an exact HTTPS origin, resource its exact `/mcp`. Discovery implements RFC8414 and RFC9728 (root and resource-path metadata), S256-only PKCE, public client registration, exact redirect URI matching, resource binding, opaque short-lived access tokens and rotating refresh token families. No wildcard/relative/fragment/credential redirect URLs; HTTP only for literal loopback registration. Authorization code lifetime is one minute, authorization request ten minutes, access fifteen minutes, connection thirty days. Tokens/codes are 256-bit random; persistence accepts only SHA256 digests. PKCE verifier is 43–128 unreserved characters; no plain challenge.

`firstParty.authenticate(request)` must verify the **same** native/web Carry account and a current enrolled non-OAuth session. It returns `{accountID,sessionID}`; user metadata, supplied account IDs or unverified JWT decoding do not establish identity. `verifyCSRF(request,session)` must independently validate a same-origin session-bound anti-CSRF proof. It may inspect a clone, not consume the handler's request body. State-changing owner endpoints additionally require exact `Origin=accountOrigin`. The account website should expose a same-origin proxy to this private first-party boundary; it must not forward client-supplied identity headers.

A browser consent page reads `/oauth/requests/{id}` and submits its own actual user selection to POST at that path. It displays registered client name together with the exact client ID and redirect destination (a dynamically registered name is untrusted display text, not verified brand ownership), requested scopes, precise selected trips, only-new-trips option and independent library/files/preferences/private-booking permissions. AI never approves this endpoint with its MCP bearer. On approval, the store checks every selected trip actually belongs to this account. It atomically consumes the pending authorization and creates a grant plus single-use code bound to original client/redirect/resource/challenge/state. A forged `confirmed=true` is an unknown field, not evidence of consent. Denial redirects only to the stored exact redirect URI.

`resolveAccess` checks token expiry, current family/grant revocation, account enrollment/deletion and exact resource **every request**. OAuth grant revocation and account deletion block already-issued access tokens; signature/expiry alone are insufficient. A normal first-party browser logout need not revoke separately authorized AI connections; connection/token revocation does. Token rotation atomically consumes an old refresh token. Reuse of a previously spent valid family token revokes the family/grant. A token from a different client cannot revoke another client's connection by presenting an arbitrary client_id.

## Required durable store methods

Each input carries `now` (milliseconds), account/grant/session identifiers and immutable request bindings as applicable. Errors must use `AIFailure` with a public code; raw SQL/provider/travel text must never escape.

Required returned grant shape: `{id,accountID,resource,scopes,tripIDs,createdTripIDs,onlyCreated,expiresAt,revokedAt}`. `createdTripIDs` is exclusively populated by atomic successful execute, not MCP input; only-created connections never receive all current/future trips automatically. Scopes are `trips:read/write/create`, `library:read/write`, `attachments:read/write`, `preferences:read/write`, `private:read/write`, `exports:read` (colon expanded separately). Write/create grants require the corresponding read scope. Backgrounds/photos/files are independent of booking-private fields. HealthKit, camera, device PhotoKit identifiers, system calendar overlays and StoreKit are never added by granting account scopes.

## Domain and plans

All ten account business kinds are supported through typed `create/patch/move/delete/restore/reorder` operations and specialized `create_trip/duplicate_trip`. Fields validate against the shared immutable Graph manifest; IDs/parents and scope are checked at compile time and again in final Graph transaction. Creation IDs derive from request ID/index, so retry cannot create new identities. Trip creation produces its complete days as one logical command. An operation may declare a stable `ref` label; later creations use `parentID:"@label"` or `"@label/day/0"`, so a complete plan does not need a preliminary committed trip or guessed child UUIDs. References exist only inside the compiled plan and resolve to deterministic UUIDs. Previews include before/after field values allowed by the grant, structural parents and expected versions, not merely an opaque mutation count. Duplicate excludes files/photos/backgrounds, clears private booking identifiers, resets packed state and preserves stable graph relationships. Full copy including private assets is a separate future explicit authorized operation, not an accidental fallback.

Patch carries the caller's observed baseVersion/fieldVersions; move/delete/restore/reorder require current structural/subtree baselines. Account Graph core remains the final authority for dates, time zones, costs, field conflicts, cascade batches, concurrent descendants and asset ledger references. Graph kinds are not a license to accept arbitrary JSON fields or raw account IDs. Root order is restored/created before children; deletes deepest first. Duplicate entity operations in one plan are rejected, requiring a single explicit combined mutation rather than silently overwriting one action.

`preview_plan` stores a whole immutable plan; `apply_changes` does ordinary unambiguous small edits immediately and automatically produces a preview for deletes/restores, date changes, duplicates and compound or large changes. Any request ID already bound to an explicit preview must commit through that approved preview, even if its edits would normally qualify for immediate application; apply_changes cannot bypass an existing pending preview. Preview response has an `approvalURL` to a first-party page and no confirmation bearer. Owner approval binds contentHash; commit uses the same original request ID and whole command. Inverse undo goes through the same path. `saved_to_account` confirms only durable graph/receipt acceptance. Device display/calendar/notifications/Widget/Live Activity remain `not_observed`/deferred.

`read_attachment` is chunked ≤64KiB, rechecks current grant per call and proves asset is referenced by an authorized member of the requested trip. Optional `readAsset` store method must additionally bind current ledger/version and entitlement in its own transaction; return `{bytes:Uint8Array,hasMore}` without signed/provider URLs. Optional `prepareExport` must generate a first-party reviewed export preview honoring file/private scopes; creation never implies third-party sending. Search/flight/recommendation/route adapters receive only redacted authorized graph plus input; install actual server adapters before claiming availability. No MapKit proxy or HealthKit fallback is installed here.

The PostgreSQL implementation is now in `postgres-store.mjs`, with a pool transaction driver in `postgres-driver.mjs` and a private, uninstalled schema draft in `postgres-schema.sql`. It is verified through real local PGlite SQL, not deployed. `core.assertAccount(tx,{accountID})` must lock and validate the canonical Carry account row under the SAME lock ordering as native Graph writes and deletion; the AI-specific advisory lock alone does not serialize native writers. `core.assertOwner(tx,p)` must check an actual current non-OAuth session without creating a session. `ownsTrips` verifies selected live roots. `readGraph` returns the current complete, bounded parent-linked graph needed to recheck scope, under the same account lock. `execute` applies the validated shared Graph core and obtains before/after images in this exact SQL transaction. `prepareUndo` compares accepted affected versions/subtree versions and produces a version-bound safe inverse. None of those methods may call HTTP/native-only RPCs, open a second database transaction, commit early, or return a queued job as saved_to_account.

The SQL adapter rechecks scope on the current graph and uses an approved preview's stored immutable compiled command. Refresh reuse is deliberately handled as a committed revocation result followed by invalid_grant outside the transaction; throwing within the transaction would undo the revocation. The concrete shared-core adapter is `postgres-graph-core.mjs`, verified through all portable Carry migrations and an actual SQL transaction. Migration `20261101041529_account_ai_shared_graph_core.sql` preserves native session checking, moves the pure business transaction into private service-only `graph_apply_core`, and installs the private AI schema/explicit role grants. The FK removes account records when Auth deletes the user; active-account checks block access immediately when deletion begins. Account consent/preview UI and the pooled-runtime entry exist and have local HTTP/SQL tests; Actual query/export/asset adapters now exist and have local SQL/HTTP tests; hosted deployment and hosted/native/two-device acceptance remain required. Bounded expired-record maintenance now has one private SQL implementation, shared by the Node adapter and a prepared pg_cron migration; hosted activation and execution readback remain pending. See `../../docs/carry-ai-retention-qa-2026-11-01.md`. The complete ordinary-user path is not claimed complete.


Private files and exports (local implementation): `assets.mjs` uses the service-selected private provider origin and immutable verified version. Every chunk request is bounded to 64 KiB and is authorized against current account/grant/trip, live graph slot, verified ledger and matching current Storage metadata before and after I/O. Full streamed files recheck authorization after each delayed body read and verify exact bytes and SHA-256; no provider or signed URL crosses the AI/browser boundary. Missing photo originals fail full backup with `photo_original_required`; thumbnails are never presented as preservation of originals.

`prepareExport` durably records a 10-minute immutable request/graph/manifest/content hash in the private `export` bucket. Full backup requires private, file and preference read scopes in addition to trip/export scopes; share export excludes packing, photos, files, cover backgrounds, private booking fields and reminder settings. The first-party owner session reviews actual names, destination/date, contents and filenames (up to 100 shown with explicit shown/total counts), then CSRF + HMAC approval binds the content hash. Owner-authenticated preview/download rechecks the current grant, selected live trip and native session; the selected graph and manifests must still match before streaming. Content creation, approval, download and sending are separate; no send capability is inferred.

The result is a native version-1 `CarryBackup` JSON (`.json` or redacted `.carrytrip`): full nested relations, dates/time zones/cost fields, packing state, inline thumbnails, attachmentFiles, backgroundImages with crop references, photoOriginals keyed by canonical photo UUID, and assetManifest are retained. Export selects a trip; global library and default reminder preferences are outside its scope. JSON/base64 streams in bounded 64 KiB output chunks without materializing the whole export. Each chunk, including metadata-only shares, is reauthorized before and after preparation; downstream cancellation immediately cancels an active private provider reader and aborts pending provider fetches, and any revoked access, missing version, length/hash mismatch or timeout fails the stream rather than completing a parseable partial backup. Expiry cleanup includes export records; CLI-generated migration `20261101041536_account_ai_private_exports.sql` only extends the private record kind constraint/index and is deployed to carry-dev. Hosted identity and user-approved export acceptance remain pending.

Native restore interoperability: full export preparation and pre-download revalidation reject total referenced file bytes above 128 MiB (`export_too_large`, HTTP 413) or attachment-file bytes above 25 MiB (`export_file_too_large`); other assets remain capped at 50 MiB each. Inline thumbnails count toward the aggregate budget. The native JSON entry is bounded to 256 MiB and validates the corresponding embedded-byte budget without silently omitting assets.

The full JSON envelope is independently capped at 256 MiB: AI preparation and pre-download validation count actual UTF-8 metadata/manifest JSON, exact base64 expansion and every inserted property/comma; no provider fetch is needed to enforce this. The local SQL-to-stream contract test compares the estimate to actual serialized output length and exercises the rejection threshold. Native async decode/staging rejects duplicate business UUIDs or more than 20,000 entities before model construction, and new/legacy native export also rejects encoded output over 256 MiB.
