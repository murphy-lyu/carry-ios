# ADR：Carry 账户身份与独立数据服务

日期：2026-10-25。

状态：**产品方向与可选账户已确认；Apple 登录作为首选。服务商/同步实现为待验证的工程选型，未配置生产身份或迁移用户数据。**

用户同意在适合产品时使用 Apple ID 登录，不再受原纯 iCloud 方案“不引入 Apple 登录”的约定限制。本 ADR 落实 `specs/carry-cloud-and-ai.md`，不重做与旅行无关的账户体系。

## 1. 采用的身份体验

- Apple 原生 App 使用系统 AuthenticationServices 的 Apple 登录；MCP 授权页在浏览器使用对应的网页 Apple 登录，进入同一个 Carry 账户。
- 登录是使用者自己的 Apple 身份。账户持有人 Bing Xue 的开发者账号继续只用于发行和配置，不要求用户把系统 iCloud 切到该账号。
- 本地功能无需登录。打开云同步或连接 AI 时才出现登录入口；不在启动页增加强制注册或姓名/头像填写流程。
- 不引入自管密码、额外短信验证或强制邮箱验证。网页也能使用 Apple 登录，当前不为未来平台提前堆叠全部登录方式；保留提供者身份映射，日后可受控增加恢复方式。

Apple 登录适合当前 Apple 平台产品，不能独立解决旅行存储、离线同步或 AI 权限。相较自管密码可减少密码找回、短信/邮件发送及敏感凭据维护；这项判断不等于声称它是任何平台、任何用户的唯一最佳选择。

## 2. 身份边界

以服务端内部 account ID 标识 Carry 账户，外部 provider subject 作为已验证身份映射。不使用邮箱、姓名、设备 ID 或开发者 Team ID 直接充当用户身份。私密转发邮箱、缺失姓名和首次授权后不再返回姓名都应正常工作。

原生 App ID 与网页 Services ID 需按 Apple 官方关联配置核对。不能凭邮箱相同自动把两条身份合并，也不能假定不同 client audience 天然返回相同 subject；上线门禁是原生/浏览器真实登录命中同一账户，反例命中不同账户。

由成熟认证实现完成令牌签名、issuer、audience、时效和 nonce/state/PKCE 等适用校验；App 接收到 identity token 不等于身份已验证。只在服务器保存必要的提供者凭据，并用于撤销流程，不把 Apple token 当作 Carry API 或 MCP 的通用访问凭据。

Carry 的设备会话与 AI 授权分别管理。一个新的 AI 连接需独立的授权范围；复用浏览器登录会话只降低登录成本，不自动批准行程读取。所有旅行 API 用服务端验证过的身份寻址，忽略客户端传入的 owner/account 声明。

## 3. 认证与数据服务选项

| 选项 | 优点 | 对本项目的代价 | 当前判断 |
|---|---|---|---|
| Apple 登录 + 自建完整认证/会话系统 | 全部可控，直接接既有 Worker | 需要长期正确维护 OAuth 会话、撤销、轮换、回调、令牌和删除，不应由登录按钮简单替代 | 不优先 |
| Apple 登录 + 成熟托管认证 + Postgres/文件存储 | 原生及网页 SDK、成熟会话，关系数据和事务适合复杂旅行图；减少密码认证自研 | 需要验证账户归并、Apple 撤销生命周期、地区网络、备份/恢复、供应商可迁移性和费用 | **优先验证；Supabase 为具体候选** |
| 继续用设备私人 CloudKit 作为唯一写入端 | 改动少，原生集成已有 | 不能满足本项目已确定的账户 API 执行路径；改用网页 CloudKit 仍需重新验证存储协议/身份，不能直接写 SwiftData 管理的内部记录 | 不作为最终方向 |

Supabase 文档确认支持原生和网页 Apple 登录，适合进入候选，不表示已经完成部署或确认了国内可达性。保留现有 Cloudflare 作为自营 API/MCP 入口的选项，旅行写操作必须走同一领域命令事务；不能把宽权限数据库 service key 发给 App 或 AI。

不要仅因现有原型用 SQLite 就确定所有用户共用一个 Durable Object。账户隔离、关系查询、事务、删除、导出和可恢复性先于供应商惯性；生产存储按风险原型结果确定。

## 4. 同步选项

| 选项 | 主要取舍 | 当前判断 |
|---|---|---|
| SwiftData 独立账户库 + 领域命令/outbox/游标同步 | 可复用大量原模型和 UI，复杂合并规则可显式控制；所有写入口和删除/迁移必须完整接入，自研同步可靠性工作量高 | 保持优先候选，先验证真实事务和重启路径 |
| 成熟同步引擎 + 官方 SQLite/GRDB 接口 | 同步传输、持久队列与订阅由成熟 SDK 支撑；并不自动替我们定义冲突/删除/整套计划事务；还需评估模型/UI 改造 | 与前项比较，PowerSync 官方 Swift SDK 为候选 |
| 社区 SwiftData 透明适配层 | 表面改动小 | 当前公开适配器声明使用私有 SwiftData 接口，存在 SDK 漂移与数据损坏风险；不作为长期数据层 |
| CloudKit 与自建服务同时自动写同一行程图 | 看似保留两边功能 | 双方同步归属不清，回环、重复、删除复活和冲突不可控 | 拒绝 |

先定义领域操作和一致性契约，再选择传输/存储适配。不能将 SDK 的“支持离线”当作 Carry 的所有日期调整、排序、文件迁移和多设备冲突已被解决。

## 5. 删除、退出与运维

- 普通退出：结束该设备会话，按账户隔离缓存；存在未同步编辑时明确保留/导出选项，不清除他人或另一个账号的数据。
- 撤销 Apple 身份：拒绝旧身份继续授权，处理提供者通知和系统凭据状态；不会只隐藏登录 UI。
- 删除 Carry 账户：App 内可发起，重新确认影响范围，撤销 Apple 及 Carry/AI 凭据，停止下载/上传并执行账户数据和文件删除作业；重试幂等。删除失败给出可追踪状态，不把“请求提交”当删除完成。
- 未授权迁入的本地/iCloud 源数据不随账号删除自动抹除；账户备份、保留期与物理删除边界需在实现时明确。
- 网页 Apple 登录有 client secret 轮换维护要求。上线前必须有到期检查、轮换手册与真实演练；不通过聊天记住 `.p8`，不在仓库保存秘密，也不擅自创建提醒或自动化。

## 6. 当前风险验证与证据边界

`scripts/carry-cloud-prototype` 是无网络、无身份提供者、合成账户的 SQLite 算法原型。实际磁盘事务验证不同字段合并、同字段拒绝、整套计划回滚、提交故障、幂等/重启、账户寻址隔离、删除防复活与分页重放。

该原型不含用户认证、真实手机离线库、文件迁移或生产数据库适配；不能作为完整同步/安全验收，也不直接部署。下一步需要并列验证本地事务 outbox、文件复制与校验、原生/网页同账户登录及代表性网络，再定服务商和工期。现有真实服务的网络超时独立排查，不能靠改架构视为解决。

## 7. 上线前配置清单

- [ ] 核对正确发行团队的原 App ID、原生 Apple 登录 capability、关联 Services ID、网站域名与精确回调地址，禁止通配重定向。
- [ ] 认证候选的实际原生 SDK/网页流程、匿名态/退出/刷新/撤销测试，原生与网页命中相同 Carry 账户。
- [ ] 提供者 secret 的安全存储、轮换和 Apple 撤销端到端核对；不在 App/日志/仓库存服务端私钥。
- [ ] 账户资源隔离与每连接行程授权，两种 token 不能互换或放大权限。
- [ ] 完整数据/文件同步方案定稿、存量迁移、旧构建分叉、备份恢复演练。
- [ ] 代表性中国与海外网络验收；认证与数据存放目的地确定后更新隐私政策/数据声明。
- [ ] 所有业务入口、九语言、原生真机、两轮完整验收和自行 Review。

这些配置在实施到对应阶段时完成；当前无需用户重新登录开发者网站或先提供密钥。
