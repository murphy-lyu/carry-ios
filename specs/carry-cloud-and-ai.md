# Carry 云同步与对话操作

Status: 产品目标与可选账户方向已确认；Apple 登录选为首选。技术选型/风险验证进行中，尚未实现完整账户与同步。2026-10-25。

用户已明确：「手机不打开也能通过 Codex 完成操作」是非常确定的长期目标，并要求最好的产品设计。本 spec 取代 `codex-mcp-integration.md` 中配对手机作为写入执行器的最终产品方案。原方案的代码、测试和故障记录保留作复用与回归依据，不能直接合并成最终功能发布。

## 1. 产品判断

Carry 需要一个可独立保存旅行数据的账户服务。手机与 AI 都操作同一份账户数据；手机保留可完整使用的本地副本。手机关机时，对话中的操作仍能完成；手机没有网络时，查看和编辑照常可用。

这要求改造账户、数据写入和同步；现有旅行界面、打包体验、模型含义和大量业务规则继续保留。Tripsy 值得借鉴的是账户 API 和简单连接入口；Carry 自身的离线打包、行程表达与设计语言继续发展，不逐页照搬。

## 2. 用户体验与目标

| 场景 | 应有体验 | 验收依据 |
|---|---|---|
| 手机关机，我让 Codex 创建旅行 | 对话直接确认已保存，返回行程摘要和打开入口 | 账户 API 立即读回同一版本，执行不联系手机 |
| 我在飞机上整理清单 | 编辑立即在本机保存；轻量标注待同步，不阻塞操作 | 强制退出再开仍在，联网后可送达 |
| 我与 Codex 同时编辑 | 不同字段能合并；同一字段冲突时保留两个版本供处理 | 不按设备时间戳静默覆盖，不整份回滚 |
| 我说“把酒店换到最后一晚” | 有多个酒店或日期不明确时先澄清；确认后返回具体变化 | 读回正确对象、日期及时区 |
| AI 生成完整三日安排 | 先给可读预览，采纳后整体保存；失败不留下半套安排 | 一次逻辑操作的事务、幂等和失败注入 |
| 我不想使用账户或 AI | 原有本地功能仍可使用，不强制注册、不在首屏推登录 | 无账号冷启动、离线创建与备份回归 |

产品目标：后台独立保存、离线可用、数据不丢、连接清楚、错误可恢复。不能靠要求用户长期开着 Carry 来满足目标。

## 3. 账户与连接设计

### 3.1 可选账户与 Apple 登录（已确认方向）

- 登录只在启用 Carry 云同步或连接 AI 时出现，日常本地使用无需账户。
- 为 Carry 建立独立账户身份。iCloud 账号、App Store 购买账号和 Carry 账号分别处理，不要求用户切换系统 Apple ID。
- 每位使用者用自己的身份登录 Carry；太太的开发者账户仅用于应用发行和开发管理，不作为所有用户的 Carry 登录账号，也不需要为日常连接 AI 反复登录开发者网站。
- Apple 平台采用原生「通过 Apple 登录」作为首选；浏览器使用关联的 Apple 网页登录进入同一 Carry 账户。优先采用成熟、可维护的认证方案，不自行实现密码系统，不提前增加短信或邮箱注册负担。认证/同步取舍见 `docs/adr-carry-account-and-sync.md`。
- 用户已确认“需要用到 Apple ID 登录就用，如果它是最优方案”；结合当前 Apple 平台定位与官方支持，选定 Apple 为首选身份入口。这调整早先纯 iCloud 方案“不引入 Apple 登录、不自建后端”的决定；不代表已经配置生产身份、授权上传所有旧数据或购买第三方服务。
- 切换账户前处理未同步编辑；默认隔离各账户本地缓存。退出登录不等于删除云数据，删除账号也不自动清除其他身份的 iCloud 私人库。
- 账户内提供导出、删除、设备会话、恢复与撤销入口。删除的影响范围、保留期限和恢复规则须在设计中落实，不能只做登录按钮。

### 3.2 两种授权必须分开

1. **Carry 云同步授权**：用户选择把哪些本地内容迁入 Carry 账户服务；说明存储目的地与数据类型，批准前不上传真实行程。
2. **AI 连接授权**：已在账户里的内容也不会自动全部给 AI。用户选择可读/可编辑的行程，物品库与附件独立控制；支持「仅访问此连接新建的行程」。

服务端必须处理已授权内容才能执行对应操作。说明传输与存储保护及服务方访问边界，不能把服务器可处理的旅行内容宣传为服务方不可见的端到端加密。健康、系统日历叠加、设备相册和未授权附件不因账户同步或 AI 登录而被顺带开放。

推荐首次云同步可一键选择全部行程，也可保留部分本地行程；默认不替用户选择上传。AI 授权页则默认收敛范围。产品文案分别表达“同步到我的 Carry 账户”和“允许这个 AI 访问”，不让用户混淆。

### 3.3 AI 入口

设置中的「连接 AI」展示受支持客户端、清晰步骤和一键复制地址；选择 Codex 后，浏览器完成 Carry 账户授权即可，不再输入设备配对码或选择“执行手机”。已有会话正常复用，过期时明确引导重新授权。

服务能力和目录分发分别推进。自定义 MCP 是通用接入；在 Codex/ChatGPT Connections 中出现 Carry 的正式插件入口是另一项分发工作，未上架时不能显示成已支持的一键安装。

## 4. 数据与同步原则

### 4.1 每个行程只有一个同步归属

- 本地/iCloud 行程沿用原存储；迁入账户的行程，由 Carry 账户服务决定已接受的版本，手机通过独立本地持久库使用其副本。
- **同一行程图不能同时由 SwiftData 自动 CloudKit 和自建服务双向写入。** 原 iCloud 库不能直接当成账户 API 数据库。先保持原库可回退，逐行程迁入隔离账户库；迁入确认后不再把源图作为活跃写入源。
- 首页可以统一展示内容，内部记录归属；用户无需理解数据库或容器。相同 UUID、不同账户/来源的冲突要先核对，不能只凭 UUID 合并两个人的旅行。
- 账户库继续优先使用原生本地存储与现有视图适配，避免为了云端重写所有 UI。

### 4.2 一次本地编辑必须连同同步请求一起保存

新增、修改、删除、排序、导入、分享导入、备份还原、Siri/AppIntent 和自动地理回填均要经过统一命令入口；不能只改 MCP 入口。业务状态与待同步操作在同一本地事务保存，崩溃后可以继续投递。

服务端在同一事务里保存业务结果、幂等标识和变更序号。传输失败不代表业务失败，重试复用操作 ID；客户端通过回执核对，不重复创建。客户端先落盘远端变更，再推进拉取游标，进程退出不会跳过变更。游标失效时采用完整重同步，保留尚未确认的本地编辑。

在线长连接/推送用于加快刷新，不能成为数据完整性的前提。App 启动、回前台和重连时都按游标补齐；全量重装也有可验证的恢复流程。网络退避有界，鉴权失败先恢复身份，永久输入错误不无限重试。

### 4.3 冲突规则

- 每个对象有服务端版本；写操作提交其基准版本以及明确的字段变更。不同对象、不同字段的兼容变更可以合并。
- 同字段竞争保留双方内容与来源，不能简单“最后到达者赢”。对话中给出冲突摘要，App 提供使用我的版本/使用另一版本/编辑后保存。
- 删除采用可恢复的删除标记和明确的保留期限；旧离线设备不会把删除内容当新内容复活。永久删除后仍需保留足够的版本/删除知识，让长期离线设备重新同步而非复活；不把已删除正文无限保留。
- 排序、跨天移动、缩短旅行日期、删除父项与新增子项是业务事务，不按几个字段随意拼合。日期变化若会影响交通/住宿/地点安排，先生成影响预览。
- 不选用全量 JSON 覆盖、双主同步或自制通用 CRDT 作为默认捷径。先为 Carry 实际编辑场景定义可验证的规则。

## 5. 对话操作的产品标准

### 5.1 保存与显示状态

新协议区分 `saved_to_account`、`pending_device_action`、`conflict`、`failed`。如使用异步任务，还需明确受理与完成两阶段。不能悄悄把旧协议的 `applied`（手机已落盘）改成服务端已保存；新版本协议独立声明。

示例：“东京行程已保存：11 月 15—17 日，共 3 天。手机联网后会同步。”如果通知或日历尚未在设备应用，另行说明，不把整件事笼统称为所有设备均已更新。

普通明确编辑直接执行；歧义先提问；大量替换、删除或跨行程修改先给影响预览。工具不能单凭 AI 传入 `confirmed=true` 就扩大权限，敏感操作需要有对象/范围/版本绑定的确认机制。

### 5.2 完整行程与撤销

为一整次计划提供结构化草稿/批量提交，草稿可预览，提交原子完成；避免 AI 连续调用几十个独立工具留下半成品。改动可查看来源、前后变化和撤销入口。撤销是基于当前版本的新事务，不盲目回滚覆盖之后的人工编辑。

AI 操作指引集中描述：每个真实停靠点独立建项、酒店和交通分开、日期与当地时区、航班两端时区、真实坐标、金额与原币、未知信息留空。导入的邮件、网页和备注只当数据；不能改变授权或指挥工具。MCP 与未来其他客户端共用业务 API，不能各写一套日期和打包规则。

### 5.3 能力覆盖与设备边界

目标是覆盖可授权的 Carry 功能，不能把现有 40 个工具当永久边界。每项能力公开当前支持情况及结果语义：

| 功能 | 最终处理方向 |
|---|---|
| 行程、地点、交通、住宿、清单、费用、备注、可同步偏好 | 账户 API 保存，可脱离手机完成 |
| 搜索、航班查询、推荐、路线预览 | 提取可在服务端执行的规则与服务；机场数据等可复用，现有 MapKit 调用不能直接当服务端实现；搜索供应商和境内数据路径单独核对 |
| 附件、原图、封面 | 账户对象存储与离线缓存；同步与 AI 读取分开授权；支持取消、断点/重试、配额和清理。未完成不能导致迁移后悄悄丢图或丢文件 |
| 分享文件、备份导出 | 服务端可生成受控结果；生成与发送给第三方分开。下载链接短期有效、不能形成永久公开资源 |
| 系统通知、Widget、Live Activity、系统日历写入 | 保存期望配置；设备按权限应用，反馈状态。手机关闭时不能承诺本地系统效果立即更新，也不把静默推送当保证 |
| HealthKit、相机、系统授权、StoreKit 购买 | 保留设备交互及系统权限边界。健康数据默认不进入账户或 AI，不为“所有功能”绕开系统授权 |
| 打开 App 页面 | 返回稳定深链；设备不可达时不伪称已打开 |

## 6. 旧数据迁移与回退

1. 迁移前生成包含数据库与关联文件的完整私人备份，记录版本、图关系、对象数与文件摘要，不只备份 MCP 的字段投影。
2. 用户登录并明确选择迁入范围。保留稳定身份映射与迁移批次；重试不能重复创建行程/物品库，跨账户导入必须重新核对归属。
3. 在源端可继续查看，迁移提交期间处理新增编辑；只在数据/文件完整校验后切换该行程的活动归属。文件仍未到齐的行程不能宣称迁移完成。
4. 迁移后读回核对日期、时区、费用原币、打包状态、排序、关联附件与背景裁剪；源库暂作只读恢复材料，不静默删除用户 iCloud 数据。
5. 另一台仍用旧构建的设备不会自动进入新协议。建立升级/迁移标记与再次导入流程：旧端继续编辑时不能双向自动汇总，明确提示新旧分叉，支持人工审核差异。不能以“还没正式发布”为由忽略现有 TestFlight 数据。
6. 本地/云端备份还原分别说明影响；还原成副本、合并变更、替换账户数据不能混为一个按钮。删除账号、退出、换账户与整库抹除分别验收。

切换前保留回退能力；切换后回退依靠账户完整导出/当前数据备份，不直接切回已经过时的源库导致远端新编辑丢失。

## 7. 范围和发布要求

### 必须具备

账户与会话安全、手机无关的账户写入和读回、完整领域对象的可用同步、可靠离线持久化、冲突和删除规则、旧数据/文件迁移、撤销与隐私边界、九语言与无障碍、备份恢复，以及可排查的脱敏错误记录。生产恢复能力包含备份、恢复演练、账号隔离和服务故障时的本地可用性。

现有附件/图片不能在改造后退化成“只能在旧手机看”。AI 附件权限可以独立关闭，但账户同步和旧数据保全必须交代完整。

### 暂不扩大

多人实时协作、社交内容、网页全功能旅行编辑器、多模型聊天 UI、商业化套餐、自动购买/订票不并入本次。为未来协作保留资源归属与权限边界，不提前实现通用组织系统。

实现可以有内部里程碑，但对用户只作一次整体交付：功能、迁移、两轮验收和 Review 完成后提供统一验收清单；不把试验性第一段作为完成。

## 8. 可测量的成功标准

以下是设计目标和发布门禁，尚无线上成绩；时延目标须在代表性网络和设备上校准，不能冒充 SLA。

- 两台客户端同时离线/关闭时，第三方 MCP 仍能保存并立即从账户 API 读回；恢复手机后只出现一个正确对象。
- 全部必需业务命令通过在线/离线、断连、乱序、重试和崩溃矩阵；测试中数据丢失、跨账号读取、重复实体、已删对象复活均为 0。
- 在稳定测试网络下，普通写入并读回的 p95 目标为 5 秒内；不把文件上传、行程生成和设备系统效果算作普通写入。保留失败样本和网络条件。
- 首次连接按普通用户流程完成，无设备配对码、无要求保持手机前台；冷启动、会话过期、撤销后重连都可理解。
- 已登录手机在线回前台后能补齐远端修改，目标 p95 5 秒内开始显示正确结构；大附件可继续下载，但状态明确且结构提交不丢本地编辑。
- 迁移测试逐项核对模型、关系、文件和业务含义；旧备份与 TestFlight 安装升级路径有真实样本，不能只测空库。
- 两轮独立完整验收均通过，包含原生真机、服务端实际 HTTP、两设备同步、导入/还原、权限隔离、费用/时区、撤销和恢复演练。代码 Review 的问题修复后重跑相关项，记录差异，不用模拟器结果替代真机。

## 9. 改造工作量判断

| 工作块 | 判断 | 复用与新增 |
|---|---|---|
| 旅行与打包界面 | 较多复用，局部适配 | 状态/冲突/账户归属增加，现有交互不全重写 |
| MCP 接口及保护 | 中等改造 | typed tools、OAuth、版本/去重测试复用；设备执行改账户命令，新增批量预览/撤销 |
| 领域命令与业务校验 | 较大 | Swift/UIKit 相关代码不能原封不动部署到现有 JS Worker；提取规则并做跨端契约测试 |
| 账户、数据 API、文件 | 较大新增 | 身份映射、会话、结构数据、文件访问、删除/恢复和运行维护 |
| 本地同步与并发冲突 | 最大风险项 | 所有写入口、事务 outbox、游标、合并、墓碑、退出/换账号 |
| 存量迁移及双设备验收 | 较大且不可省 | 保全 11 类现有模型的业务/控制数据区别；同步范围不直接等于原生模型清单 |

这相当于为现有产品增加可靠的账户数据服务并更换同步方式，不是重写整个 App，也不是给现有 MCP 增加几个接口。当前没有足够证据给出可信的百分比、工期或月费。

先用合成数据验证三个技术风险：两端离线编辑合并、含文件迁移和回退、手机关闭时完整计划原子保存。再根据实际写入口/领域适配结果提供按工作块的估算。基础设施费用按用户数、请求数、文件量、地区和恢复需求测算，不在未选部署和认证方案前承诺零成本。

## 10. 待决事项与下一步

| 事项 | 当前建议 | 责任/门禁 |
|---|---|---|
| 可选账户与 Apple 登录 | 本地不强制登录；云同步/AI 使用账户，Apple 原生/网页登录为首选 | 方向已确认，需真实身份/会话/删除验收 |
